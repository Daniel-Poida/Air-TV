# Air TV: экспериментальное ядро AirDrop

Статус: реализован и проверен прикладной слой, но полноценная поддержка AirDrop в Android TV пока НЕ готова. Модуль добавлен в исходный проект Air TV; установленное приложение 0.1.2 не изменено. Модуль ещё не подключён к Android-службе и интерфейсу подтверждения.

## Что реализовано

Java 8-совместимый TLS/HTTP-приёмник с `/Discover`, `/Ask`, `/Upload`. Запросы и ответы используют binary plist. Подтверждение предложения через внедряемый callback ограничено 45 секундами. Callback должен поддерживать прерывание; имя отправителя не подтверждает его личность. Подтверждение связано с сертификатом конкретного TLS-клиента и действует две минуты, на одну загрузку. В тестовом TLS-контексте принимаются самоподписанные сертификаты; это не подтверждает Apple ID.

Загрузка потоковая: raw или gzip cpio, форматы odc/newc/crc, HTTP Content-Length/chunked и Expect: 100-continue. Размер передачи ограничен свободным местом на устройстве (резерв 16 МиБ). Сохраняются ограничения на 512 архивных записей и 128 предложенных объектов. Принимаются только предложенные файлы и каталоги. Ссылки, специальные файлы, выход за каталог, дубликаты, повреждённые архивы и неоднозначный HTTP-фрейминг отклоняются. Файлы сначала записываются в отдельный временный каталог; завершённая передача публикуется переименованием. Незавершённые загрузки удаляются.

## Проверка

14 интеграционных тестов прошли на loopback 127.0.0.1, с Python plistlib как независимым клиентом и временными TLS-сертификатами. Проверены три формата cpio, каталог, Unicode, подтверждение, привязка к сертификату, запрет повторного использования, CRC, повреждённые plist/архивы, очистка файлов и HTTP-фрейминг. Отдельный тест проверяет ограниченный расход памяти при многократных ссылках на один большой объект plist. Передача синтетического файла около 32 МиБ прошла при Java heap 64 МиБ. Gradle `:airdrop-core:build` прошёл.

Это не тест передачи из настоящего Finder и не гарантия совместимости с текущей macOS. Реальный Finder не показал отдельный пробный приёмник, запущенный на том же Mac; такой тест не проверяет обнаружение отдельного Android-устройства.

Для запуска приложенных тестов нужны JDK 17+ и Python 3.10+ с `cryptography`. Из корня архива:

```sh
python3 -m venv .venv
.venv/bin/pip install -r airdrop-lab/requirements-test.txt
# JAVA_HOME должен указывать на установленный JDK.
.venv/bin/python airdrop-lab/test_protocol.py
```

Тесты компилируют исходники заново, генерируют одноразовые сертификаты и используют только синтетические файлы. При закрытии теста временные ключи и файлы удаляются. Ключей и сертификатов в архиве нет.

## Что осталось

1. Проверить возможности Wi-Fi и прошивки включённого телевизора через ADB. Во время разработки `.31` и `.55` не были доступны; `.28` пользователь выключил.
2. Реализовать транспорт обнаружения и подключения, совместимый с Finder. Обычный LAN Bonjour и HTTPS сами по себе ещё не обеспечивают AirDrop. Для исследованного OpenDrop нужен AWDL; открытая реализация OWL требует Wi-Fi с активным monitor mode и injection. Нельзя предполагать, что штатное Android TV приложение получает такие возможности.
3. После подтверждения транспорта добавить генерацию/хранение TLS-ключей, Android-службу, ограниченный режим видимости, управление жизненным циклом, свободным местом и размером передачи, окно подтверждения с пульта, список полученных файлов и открытие поддерживаемых видео. Режим «Только контакты» не реализован.
4. Проверить настоящую передачу Finder → телевизор, отмену/обрыв, параллельные запросы, фоновый режим, перезагрузку и совместную работу с AirPlay. Только после этого выпускать APK с заявленной поддержкой AirDrop.

Никакого root, перепрошивки, изменения драйвера телевизора или глобальных настроек Mac не выполнено.
